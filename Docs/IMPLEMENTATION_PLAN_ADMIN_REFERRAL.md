1. Цели и Обзор
Внедрение инструментов для управления бизнесом, повышение вирального роста через реферальную программу и обеспечение прозрачности финансовых и пользовательских метрик.
Ключевые компоненты:
Админ-панель: Управление пользователями, начисление кредитов, просмотр метрик.
Аналитика: Асинхронный расчет DAU/MAU, LTV, Retention и финансовых показателей.
Промокоды: Система генерации и активации кодов на кредиты.
Реферальная система: Атрибуция приглашений и автоматическое вознаграждение за оплаты рефералов.
2. Архитектурные Решения и Стандарты
2.1. Принцип "Асинхронной Аналитики" (Daily Aggregation)
Проблема: Прямой подсчет DAU/WAU/MAU по таблице extension_logs (которая быстро растет) при каждом открытии админки "положит" базу данных.
Решение: Внедряем таблицу DailyAnalytics. Специальная фоновая задача (Celery/Cron) раз в сутки считает итоги за вчерашний день и сохраняет их как одну строку. Админка читает только эту легкую таблицу.
2.2. Принцип "Финансовой Изоляции"
Решение: Не смешиваем реальные денежные транзакции (Tribute) с внутренними начислениями бонусов.
Реализация:
transactions: Таблица только для реальных денег (платежи от провайдера).
credit_transactions: Новая таблица для любых изменений баланса кредитов (покупка, промокод, реферал, ручное начисление, списание за генерацию). Это обеспечит полный аудит: "откуда взялись кредиты".
2.3. Атомарность операций
Для предотвращения Race Conditions (когда два запроса одновременно меняют баланс) использовать конструкции User.credits = User.credits + amount на уровне SQL, а не Python-логику user.credits += amount.
3. Фаза 1: База Данных и Модели (Backend)
Задача: Создать структуры для хранения новых сущностей.
3.1. Новые Модели (SQLAlchemy)
PromoCode
Хранение промокодов.
code (String, PK, Unique): Название (напр. "PROMO2025").
credit_amount (Integer): Сумма начисления.
max_uses (Integer): Общий лимит использований.
current_uses (Integer): Сколько раз использовали.
expiry_date (DateTime): Срок действия.
is_active (Boolean).
ReferralConfig
Настройки наград. Важно: Связь с тарифом через String, так как тарифы в коде (billing_service.PLANS).
id (Integer, PK).
tariff_plan_id (String, Unique): ID тарифа из кода (напр. "credit_1000").
reward_credits (Integer): Размер бонуса пригласившему.
is_active (Boolean).
CreditTransaction (Журнал аудита кредитов)
id (PK).
user_id (ForeignKey).
amount (Integer): Сколько кредитов начислено/списано (может быть < 0).
type (Enum/String): purchase, promo_code, referral_reward, manual_adjustment, usage.
related_entity_id (String, Nullable): ID платежа, промокода или user_id реферала.
created_at (DateTime).
DailyAnalytics (Агрегированные данные)
date (Date, PK).
new_users_count (Integer).
active_users_dau (Integer): Уникальные юзеры, сделавшие генерацию.
revenue (Float).
total_generations (Integer).
paying_users_count (Integer).
3.2. Обновление модели User
referral_code (String, Unique, Index): Уникальный код приглашения (генерировать при регистрации).
referred_by_id (ForeignKey users.id, Nullable): Кто пригласил.

4. Фаза 2: Бизнес-логика и Сервисы (Backend)
4.1. Сервис Промокодов (PromoCodeService)
create_promo(...): Создание кода админом.
redeem_promo(user, code):
Проверка существования, даты, лимитов.
Проверка в CreditTransaction, не использовал ли этот юзер этот код ранее.
Атомарное обновление: promo.current_uses += 1, subscription.credits += amount.
Запись в CreditTransaction.
4.2. Реферальная Логика (ReferralService & PaymentService)
Регистрация:
В auth_service.register: принимать referral_code.
Искать владельца кода.
Проверять Anti-Fraud (нельзя пригласить самого себя).
Записывать referred_by_id.
Начисление (Hook в PaymentService):
В методе process_tribute_webhook, после успешного начисления кредитов покупателю:
Проверить user.referred_by_id.
Если есть -> Найти ReferralConfig для купленного plan_id.
Если конфиг есть и активен -> Начислить бонусы пригласившему (User.id == referred_by_id).
Создать CreditTransaction (type=referral_reward).
4.3. Сервис Аналитики (AnalyticsService)
Сборщик (Cron/Job): Запускается раз в сутки (00:05).
Считает метрики за yesterday SQL-запросами (COUNT, SUM) по таблицам users, extension_logs, transactions.
Сохраняет в DailyAnalytics.
API геттеры:
get_dashboard_stats: Возвращает данные из DailyAnalytics за период.
calculate_retention: (Сложный SQL) Считает % пользователей, плативших в месяц M-1 и снова плативших в месяц M.
5. Фаза 3: API Endpoints
5.1. Admin API (/api/v1/admin/...)
GET /analytics/dashboard?from=...&to=...: Данные для графиков.
POST /users/{id}/credits: Ручное изменение баланса (с комментарием для логов).
GET /promocodes: Список.
POST /promocodes: Создать.
GET /referrals/config: Текущие настройки наград.
PUT /referrals/config: Обновить награды за тариф.
5.2. User API
POST /billing/promocode: Активация кода.
GET /users/me: Добавить в ответ поле referral_code и статистику (количество приглашенных).
